# Skill Routing Matrix

Use this matrix to choose a primary owner for the current engineering decision. It is deliberately small: activate the primary Skill first, add a secondary only when the request contains a real dependency on that concern, and do not activate the entire delivery chain by default.

| User signal or decision | Primary Skill | Allowed secondary Skill | Do not activate by default | Combine or escalate when |
| --- | --- | --- | --- | --- |
| Overall engineering analysis, uncertain Skill choice, global rule governance, or proportional process | `engineering-philosophy` | Any focused Skill that owns a discovered decision | All specialists merely because they are available | The request contains two or more independent decisions or a rule may be promoted globally |
| Architecture boundary, DI, Port, Adapter, interface ownership, package direction, infrastructure isolation | `architecture-boundaries` | `ddd-lite` for a discovered business invariant; `systematic-debugging` for an observed failure | `ddd-lite` for a technical word such as “service”; `planning-and-task-breakdown` for a direct small decision | The technical boundary is driven by domain consistency or evidence shows a boundary-related defect |
| Aggregate, Value Object, entity identity, invariant, lifecycle, domain language, bounded context, domain event | `ddd-lite` | `architecture-boundaries` for technical translation or dependency direction; `spec-driven-development` when the business rule is unclear | `architecture-boundaries` merely because a repository or service exists | A business invariant crosses a technical adapter or two contexts need explicit translation |
| Bug, exception, timeout, regression, unexplained behavior, failed test/build/deployment | `systematic-debugging` | `test-driven-development` for a regression test; the relevant technical Skill only after evidence identifies that concern | `architecture-boundaries` or broad refactoring before evidence | The failure is stable enough for a minimal experiment and the fix needs a focused regression test |
| Unclear requirement, acceptance criteria, constraints, non-goals, or material product decision | `spec-driven-development` | `planning-and-task-breakdown` after the problem is clear | TDD, review, Git, and CI as ceremony | A missing answer changes the implementation materially and needs user confirmation |
| Clear goal with several tasks, dependencies, risks, or coordination | `planning-and-task-breakdown` | `incremental-implementation` for a migration or large change | `spec-driven-development` when the goal and constraints are already clear; TDD before implementation starts | The plan has overlapping ownership, irreversible steps, or dependencies that require checkpoints |
| Large refactor, migration, compatibility period, or vertical-slice sequencing | `incremental-implementation` | `test-driven-development`, `architecture-boundaries`, or `ddd-lite` for the slice's decisions | Full rewrite, full layered scaffolding, or a second planning document by default | The old and new paths must coexist or a safe removal condition is not yet proven |
| New observable behavior, Red-Green-Refactor, behavior test, or regression test implementation | `test-driven-development` | `incremental-implementation` for cross-layer slices; `systematic-debugging` when the red state is unexpected | `code-review-and-quality` or a full plan for one focused behavior | The behavior is unclear, the failing test is a fixture problem, or the change spans multiple deployable slices |
| PR/MR, diff, merge readiness, correctness, maintainability, or review evidence | `code-review-and-quality` | `architecture-boundaries`, `ddd-lite`, `test-driven-development`, or `systematic-debugging` for a finding that genuinely belongs there | `systematic-debugging` for a review request with no active failure | A finding exposes an actual failure, a missing behavior test, or a boundary/domain decision |
| Branch, commit, tag, version, changelog, history hygiene, release notes | `git-workflow-and-versioning` | `ci-cd-and-automation` for release automation; `code-review-and-quality` for review evidence | CI/CD merely because a tag is mentioned | The release needs an automated gate or the user asks to publish externally |
| Pipeline, quality gate, build/test automation, release verification, deployment health, rollback | `ci-cd-and-automation` | `systematic-debugging` for a failing pipeline; `git-workflow-and-versioning` for version/tag mechanics | `code-review-and-quality` or Git history rules unless requested | A gate failure is reproducible and needs diagnosis, or deployment requires an explicit stop/rollback decision |

## Routing rules

- A keyword is a signal, not a decision. “Service”, “repository”, “interface”, or “CRUD” alone does not activate DDD or architecture work.
- An actual failure takes precedence over speculative redesign. Investigate it with `systematic-debugging` before changing architecture or process.
- A clear goal with complexity belongs to planning; a large or risky implementation then adds incremental implementation. Do not make planning replace a missing specification.
- TDD starts when a behavior is sufficiently clear to test. It does not require tests for every private function or a full workflow for a typo.
- Review evaluates an existing change; debugging investigates an active failure. They may collaborate after a review finding is reproduced.
- Use the smallest set of Skills that can own the decision and its verification evidence.
